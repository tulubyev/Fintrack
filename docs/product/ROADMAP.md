# FinTrack — дорожная карта этапов 1–3

Основа: «Стратегия FinTrack 2027» (октябрь 2026) и разбор кода `tulubyev/Fintrack` (ветка `main`, коммит `b3531d8`).
Спецификации эпиков лежат в `epics/`, открытые решения владельца — в `DECISIONS.md`.

Оценки даны в рабочих днях одного разработчика среднего уровня, который знает стек (TypeScript, Express, Drizzle, React). Ревью и проверка на реальных выписках входят в оценку. Ожидание модерации в сторах не входит.

## 0. Исходное состояние и зависимость от этапа 0

Этап 0 «Безопасность и честность» отслеживается в issue #12 и здесь не расписан. На 17.10.2026 закрыты дыры безопасности и шифрование полей (#13–#19); открыты сессии (#24), удаление моков (#25), API v1 и тесты (#26), роль админа на фронтенде (#22) и AI-эндпоинты (#23). | Префикс `/api/v1`, единый формат ошибок, курсорная пагинация, OpenAPI с реальными эндпоинтами | Все API в спецификациях описаны уже в этом формате |
| Удалены моки: `bankService.generateMockBankData`, захардкоженные ₽127 450 / ₽45 230 / ₽82 220 в `App.tsx`, декоративные модалки `ApiKeysModal`, `WebhooksModal`, `SyncModal` | E1.5 строит главный экран на пустом месте |
| Базовые тесты на права доступа (по договорённости — vitest + supertest на тестовой БД) | Каждый эпик добавляет тесты по этому шаблону |

Если этап 0 чего-то не сделал, это добавляется первой задачей соответствующего эпика. Что ещё нашлось при разборе кода и стоит сверить с исполнителем этапа 0:

- `App.tsx` после `/api/auth/verify` записывает **любому** пользователю `role: 'admin', adminRole: 'super_admin'` (строки 85–86). Админские маршруты на сервере это не открывает, но пользователь видит кнопку «Админ-панель».
- `GET /api/ai/balance` показывает **любому** вошедшему пользователю баланс ключа OpenRouter.
- `routes/ai.ts` `POST /ai/chat` принимает от клиента произвольный `context` с ролями, включая `system`, — это prompt injection.
- `UserStorage.deleteUserData` удаляет только `transactions`, `accounts`, `users`. При FK из `bank_connections`, `savings_goals` и других таблиц удаление упадёт, а 152-ФЗ требует удалять данные полностью. Исправляется в E1.0-T6.
- Пользователи, созданные через ЕСИА, получают `passwordHash: ''` и телефон-заглушку `+7<timestamp>`. Если вход через ЕСИА отключить, войти они не смогут. См. D6 в `DECISIONS.md`.
- `lib/api.ts` и `hooks/useDashboard.ts` вызывают несуществующие `/api/banks/real-connect`, `/api/banks/sync`, `/api/investments/portfolio`.

## 1. Общие соглашения (обязательны для всех эпиков)

### 1.1 API v1
- База `/api/v1`. Авторизация — заголовок `Authorization: Bearer <access>`. Без авторизации доступны только эндпоинты, где это прямо указано.
- Формат ошибки:
  ```json
  { "error": { "code": "VALIDATION_ERROR", "message": "Сумма должна быть больше нуля",
               "details": [{ "path": "amount", "message": "…" }], "requestId": "01J…" } }
  ```
  Коды берутся из `ErrorCodes` (`artifacts/api-server/src/middleware/types.ts`). Добавляются: `PLAN_LIMIT_REACHED`, `UNSUPPORTED_FILE`, `IMPORT_STATE_CONFLICT`, `ACCOUNT_ARCHIVED`, `CURSOR_EXPIRED` (E2.1), `AI_UNAVAILABLE` (E2.4).
- Чужой ресурс → `404 RESOURCE_NOT_FOUND`, а не 403: так нельзя перебором узнать, какие id существуют.
- Деньги передаются **строкой** с двумя знаками после точки (`"-1234.50"`), валюта — ISO 4217. В числа JS суммы не превращаются (см. D11).
- Даты: дата операции — `"YYYY-MM-DD"` (локальная дата пользователя), моменты времени — RFC 3339 в UTC.
- Списки: `?limit=50&cursor=<opaque>` → `{ "items": [...], "nextCursor": "…" | null }`. Курсор — base64url от `(ключ сортировки, id)`. `limit` не больше 200.
- Идемпотентность создания: клиент может передать собственный `id` (UUID). Повтор с тем же `id` и тем же телом вернёт `200` с существующей сущностью, с другим телом — `409 DUPLICATE_RESOURCE`. Это защищает от двойного клика сейчас и от повторов из офлайн-очереди в E2.1.
- Удаление мягкое: у синхронизируемых таблиц есть `deleted_at`. Обычные GET удалённое не возвращают, `/v1/sync` (E2.1) возвращает.
- Каждый эндпоинт описывается в `lib/api-spec/openapi.yaml` (тег = ID эпика). Orval генерирует клиентов в `lib/api-client-react` и `lib/api-zod`. Сервер валидирует тело запроса схемами из `@workspace/api-zod`. Ручной `lib/api.ts` фронтенда постепенно заменяется сгенерированными хуками.

### 1.2 База данных
- Начиная с E1.0 схема меняется **только миграциями** (`drizzle-kit generate` → SQL в `lib/db/migrations` → ревью → применение под `tulubyev` по `docs/DEPLOY.md`). `push` больше не используется.
- Новые таблицы: `id uuid default gen_random_uuid()`, `created_at`/`updated_at timestamptz` (в новых колонках `withTimezone: true`), FK на `users` с `ON DELETE CASCADE`.
- Синхронизируемые таблицы (`accounts`, `transactions`, `categories`, `budgets`, `savings_goals`, `goal_contributions`, `recurring_series`, `category_rules`) получают `updated_at` (обновляется при каждой записи), `deleted_at` и индекс `(user_id, updated_at, id)`. Это закладка под E2.1.

### 1.3 Права
Каждый запрос фильтруется по `req.user.id` на уровне storage: метод принимает `userId` и **всегда** ставит его в `WHERE`. На каждый новый эндпоинт пишется тест «пользователь B не видит и не меняет данные пользователя A».

## 2. Этап 1 — MVP учёта финансов в вебе

**Цель этапа.** Пользователь в первый же день видит свои реальные траты: загружает выписки или вводит операции вручную, получает категории, бюджеты и список подписок. Всё работает в вебе и как PWA.

**Критерий выхода из этапа:**
- активация (см. §5) ≥ 35% на когорте ≥ 200 регистраций;
- импорт работает для Сбера, Т-Банка и Альфы на реальных файлах;
- главный экран без единой захардкоженной цифры;
- нет открытых багов P0/P1 по деньгам и правам.

### Срез 1a: первые пользователи

86 дней — это около 4 месяцев работы одного разработчика. Стратегия называет 1–2 месяца, и этот срок реален только вдвоём или со срезом. Предлагаемый срез **1a (≈ 50 дней)**, после которого можно открывать бету:

- E1.0 полностью;
- E1.1 без подсказок переводов;
- E1.2 P0: generic CSV/XLSX, Т-Банк, Сбер PDF, только строгая дедупликация;
- E1.3: справочник, MCC, правила пользователя, без LLM;
- E1.4: только бюджеты;
- E1.5 полностью.

**Срез 1b (≈ 36 дней):** Альфа, ВТБ, Озон, Яндекс, нечёткая дедупликация, LLM-фолбэк, цели, E1.6, E1.7.

## 5. Продуктовые метрики

Источник данных — таблица `product_events` (E1.0) и продуктовые таблицы. Считаются SQL-запросами по расписанию, витрина — Metabase или страница в админке (D10).

| Метрика | Определение | Как считается |
|---|---|---|
| **Активация (A1)** | Доля новых пользователей, у которых через 24 ч после регистрации есть **≥ 30 своих операций** | Когорта = `users.created_at` за день. Операция «своя» — `transactions` с `deleted_at IS NULL`, `type IN ('expense','income','transfer')`, `source IN ('manual','import','notification','bank_api','receipt')`, `created_at <= users.created_at + 24h`. Корректировки баланса не считаются. |
| Активация, ранний индикатор (A0) | Доля новых пользователей с ≥ 1 счётом и ≥ 1 операцией в первой сессии | По событиям `account_created`, `transaction_created` или `import_completed` в пределах 30 мин после `auth_signed_up` |
| **Удержание D30** | Доля когорты, активной **на 28–34 день** после регистрации | «Активен» — было событие `app_opened` (веб, PWA, мобильное) или любой авторизованный запрос. Окно в неделю сглаживает выходные и малые когорты. Классический D30 (ровно 30-й день) считается рядом для сравнения с рынком. |
| D7 | То же, окно 6–8 день | Ранний сигнал |
| **Конверсия в платную подписку (C30)** | Доля когорты регистраций месяца, оплатившей подписку в первые 30 дней | `payments.status='succeeded'` по первому платежу пользователя. Дополнительно: доля платящих в MAU. |
| Ценность: подписки | Сумма в год по `recurring_series` со статусом `detected` или `confirmed` и `kind='subscription'` на пользователя с импортом за 3+ месяца | Медиана и среднее |
| Ценность: кешбэк (с E2.5) | Недополученный кешбэк за прошлый месяц, ₽ на пользователя с ≥ 2 картами | Из отчёта E2.5 |
| Деньги | ARPU = (подписки + CPA) / MAU, по месяцам | `payments` + `cpa_conversions` (E3.4) |
| MAU / WAU | Уникальные пользователи с `app_opened` за 30 / 7 дней | |

**Воронка активации** (строится по событиям):
`auth_signed_up` → `onboarding_started` → `account_created` → `import_started` или `transaction_created` → `import_completed` → 30 операций → `dashboard_viewed{has_data:true}` → `budget_created` → D7 → D30.

### 5.1 Что логировать: правила
- Имя события — `объект_действие`, snake_case, по-английски. Список событий — zod-enum в `lib/api-spec`. Неизвестное событие сервер отбрасывает и пишет warning в лог.
- Общие свойства добавляются автоматически: `platform` (`web`, `pwa`, `android`, `ios`), `app_version`, `session_id`, `anonymous_id` (до входа). `user_id` проставляет сервер из токена; клиент его не передаёт.
- **В свойствах запрещены ПДн и финансовые детали:** точные суммы, описания операций, названия мерчантов, имена файлов, телефоны, e-mail, тексты вопросов к AI. Суммы — только корзинами (`amount_bucket`: `<1k`, `1-10k`, `10-100k`, `>100k`), тексты — только длиной.
- События, от которых зависят метрики (`import_completed`, `transaction_created` с `source=import`, `payment_succeeded`), пишет **сервер**: клиентские события теряются из-за блокировщиков.

## 6. Сводка рисков уровня дорожной карты
1. **Форматы выписок меняются без предупреждения.** Нужны версии парсеров, мониторинг доли `import_failed` по `parser_code` и запасной путь через ручное сопоставление колонок. На поддержку парсеров закладывается 1–2 дня в месяц.

5. **31.12.2026 — ЕСИА.** До этой даты нужно решение D6; на этап 1 это не влияет, но пользователям ЕСИА нужен запасной способ входа.
